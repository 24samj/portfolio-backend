# Schema & migrations

`src/db/schema.ts` (Drizzle tables) is the **single source of truth** for the D1
schema. Row types are inferred from it (`typeof table.$inferSelect`) — never
hand-write a row type. `drizzle-kit` turns the schema into versioned SQL under
`migrations/`, and `wrangler d1 migrations apply` runs it (tracked in the
`d1_migrations` table).

## The loop

```bash
# edit src/db/schema.ts
bun run db:generate   # emit a new migration
bun run db:local      # apply to the local D1
bun run test          # tests run against the real migrated schema + seed
```

## Rules

- **Never hand-edit a generated migration.** To change the schema, edit
  `schema.ts` and generate a *new* migration. The applied set is immutable.
- **A migration that has never shipped may be regenerated** — delete the `.sql`,
  its `meta/*_snapshot.json`, and its `_journal.json` entry, then `db:generate`.
  Only while it is unapplied on the remote D1. Anyone holding a local D1 with the
  old version must reset it, since the tag it recorded no longer exists:

  ```bash
  rm -rf .wrangler/state/v3/d1 && bun run db:local
  ```

  Stop `wrangler dev` first — deleting the state under a running worker leaves it
  serving a deleted file and every query fails with `SQLITE_CANTOPEN`.
- **Migrations are forward-only and additive-safe.** A new nullable column or a
  new table is safe to apply to a live remote D1. A drop/rename/not-null
  backfill is not — split it across releases (add → backfill → switch → drop).
- **Rename a generated file deliberately.** If you rename a migration for
  clarity, update its `tag` in `migrations/meta/_journal.json` to match, or the
  apply step desyncs.
- **Booleans are `integer` 0/1.** SQLite has no boolean type. Convert at the
  mapper (`toWork`, …), never leak the 0/1 into an API response.
- **Fractional numbers are `real`.** `integer` silently truncates a 4.6 rating
  to 4.

## Data seed

`migrations/9999_seed_portfolio.sql` is **data, not schema**, and is generated by
`scripts/build-seed.ts` from `scripts/portfolio-data.json` — not by drizzle-kit
and not by hand. Every content change (a new job, a project description, a
skill) is an edit to the JSON followed by:

```bash
bun run build:seed
```

- Numbered `9999` so it always applies **after** whatever schema migration
  drizzle-kit generates next, and so its number can never collide with drizzle's
  incrementing ones.
- Not listed in `migrations/meta/_journal.json` — drizzle didn't create it and
  doesn't track it. Wrangler applies every `*.sql` in the folder regardless.
- Written with `INSERT OR REPLACE`, so re-applying a regenerated seed overwrites
  rather than failing on a primary-key conflict. Wrangler only re-runs it if the
  file is renamed, though: to ship a content edit, bump the filename
  (`9999_seed_portfolio_v2.sql`) in `build-seed.ts` and delete the old one.
- A column added to `schema.ts` needs a matching column in `build-seed.ts`, or
  the seed silently leaves it at the default.
